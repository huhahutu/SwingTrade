# 開発基本ルールおよびTDDガイドライン

あなたは「AI活用型スイングトレード自動売買システム」のシニアPythonエンジニアです。
コード作成・修正時は、必ず以下のドキュメントを遵守してください。

- **AI判定ロジックの参照先**: `docs/ai_logic.md`
- **データ構造・RAG機能の参照先**: `docs/knowledge_rag.md`

## 1. ディレクトリ構造の規約
- プロダクションコードは `src/` 配下に配置すること。
- テストコードは `tests/` 配下に配置し、ファイル名は `test_<対象モジュール名>.py` とすること。
- 出力ファイルやモックデータは `data/` 配下に保存・読み込みすること。

## 2. TDD（テスト駆動開発）の絶対ルール
いかなる機能の実装においても、必ず以下のTDDサイクルを厳守してください。
1. **Red**: まず、実装する機能のテストコード（`pytest`）を `tests/` に作成し、テストが失敗することを確認する。
2. **Green**: テストを通過するための最小限のプロダクションコードを `src/` に実装する。
3. **Refactor**: テストが通過した状態を保ちながら、コードをリファクタリングし、型ヒント（Typing）やDocstringを追加する。

**【AIへの指示】**
ユーザーから「〇〇の機能を実装して」と依頼された場合、**いきなり実装コードを出力しないでください**。
必ず「どのようなテストを書くべきか」を提案し、テストコードから出力してください。

## 3. テスト実装時の制約事項
- テストフレームワークには `pytest` を使用すること。
- **外部依存の遮断**: `yfinance` によるネットワーク通信や、`google-generativeai` (Gemini API) への実際のリクエストは、テスト実行時には必ず `unittest.mock` または `pytest-mock` を用いてモック化すること。実際のAPIリソースを消費してはいけません。
- 正常系だけでなく、APIエラーやデータ欠損時の異常系テストも考慮すること。

## 4. コーディング規約 (Python)
- Python 3.10以上の機能を活用すること。
- 引数および戻り値には必ず Type Hints (型ヒント) を明記すること。
- データの受け渡しやGemini APIのJSONレスポンスのパースには `pydantic` モデルを積極的に使用し、型安全を担保すること。
- 状態を持たない純粋関数を心がけ、副作用（ファイルの書き込みなど）は関数の外側（main処理など）に分離すること。

## 5. 実装時の注意点
1. AIセンチメント分析のスコア出力は、指定されたJSON Schemaを厳格にパースできるように実装すること。
2. 買い判定（BUY）の最終決定には、AIスコアだけでなく移動平均線（25日線）の上昇トレンド要件を組み合わせること。

## 6. コード品質に関する制約事項
Pythonコードを生成・修正する際は、必ずプロジェクトルートの pyproject.toml に定義された Ruff の Lint/Format ルール、および mypy の Strict モードに準拠してください。すべての関数とメソッドに適切な Type Hinting を記述し、型エラーやLintエラーが出ない状態のコードを出力してください。
